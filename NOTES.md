# Helpful analogy
## Primary skill = Woodcutting, Mining. 
- These have 1 product line -- logs, and ores. Of several tiers.

## Secondary Skill - Smithing*
- If confined only to creating Bars and Arrowheads from various ores / bars respectively, smithing is a single product line secondary skill.

## Tertiary skill - Fletching
- combines outputs from the primary product line from woodcutting and secondary (derived) product line of smithing, and, a neutral product "Feathers" that are not a skill based resource to produce arrows.

## Towns, banks, limited inventory, weapons (ideas, 2026-10-18 -- superseded in part: buildings are in the main world now, see above)
- **Towns**: a kind of node you *enter*; entering swaps your map for a submap with fixed (but still procedurally generated) interactables. Leaving puts you back where the town node is.
- **Banks, shops, etc.** live inside towns.
- **Limited inventory space**, so progression has breaks: you fill up, go to a town, deposit at a bank, withdraw later. (Also a natural "fun interruption" for long repeating actions -- the TODO in the Morning section.)
- **Combat skills as their own category**: procedurally generated *weapon classes*, acquired inside towns (e.g. bought at a shop). You can only level a combat skill once you own a weapon of that class -- so combat grows the skill tree like crafting does, instead of one fixed `combat` skill.
- **Still open**: tying crafting and combat together in a way that stays extensible (see the back-burner "how combat fits the skill tree" item under Monsters; the "each monster is its own skill" idea is one candidate, weapon classes are another, they might combine: weapon class = combat skill, monster = what it's trained on).
- Thoughts on what each would touch in the current code, for when it's time:
  - Submaps: `Position` would need a map/area id (or towns get their own coordinate space), nodes would carry which map they're on, and visibility / AOI would only consider entities on the same map. A town's layout could be a `ContentBatch` like everything else (generated once, saved, replayed), so every player sees the same town.
  - Node kinds: today every `Node` is a recipe; towns, banks and shops make it a real `kind` (`NodeDef.kind` + a branch in `GameCharacter.performOrStop`), which the notes already anticipate.
  - Bank: a second item store per character (`bank` table like `inventory`), moves between the two are one transaction. Inventory limit = a slot/stack cap checked wherever items are added (crafting, drops) -- and one-of-a-kind drops would need a rule for "inventory full" (don't drop? drop straight to the bank?).
  - Weapon classes: a new content type (like `MonsterType`) whose discovery adds a `COMBAT`-type skill per class; the shop sells a weapon item of that class; xp from fighting goes to the class of the weapon you're holding. The current single `combat` skill would become "the first weapon class" or go away.

## Monsters

- first encountered monster is monster0 
- until discovered, has a 1/2 drop rate for monster0-drop0
- only achievable 1 time _ever_
- then a 1/4 drop rate for monster0-drop1, ..., 1/8 for monster0-drop2 etc
- **Built (2026-10-18)**: drops are **one of a kind** -- each `monsterN-dropK` drops exactly once, for one player, per world, ever. Each kill has a 1 in 2^(n+1) chance (n = that monster's drops found so far) of dropping the next one; there's no other loot. The finder is told it's the only one there will ever be, everyone else hears who got it, and the drop records who found it (`found_by`).

## Persistence / multiplayer (2026-10-17)
- [x] Save game state between sessions: SQLite, server-side only. Decisions (multiple seeded worlds, atomic content batches, node capacity, 600ms server tick) and the build order are in `MULTIPLAYER.md`.
- [x] Step 0 of `MULTIPLAYER.md`: 600ms logic ticks split from 60ms render frames (`GameClock`).
  - Ticks: walking (1 tile/tick), wasd steps, action progress, and intents. `q` (start/stop) and wasd are queued and applied on the next tick, like a server would. Actions default to 2 ticks (1.2s, same as before).
  - Frames: drawing, popups (lifetimes are in frames), input. The progress bar fills smoothly using `clock.partialTick()`.
  - wasd queues at most 2 steps (`Walker.MAX_QUEUED_STEPS`) so holding a key doesn't overshoot; a wasd step replaces a hover-walk in progress. Starting an action stops walking.
  - Main loop handles every key pressed during a frame now (used to be one per frame).
  - Falls behind by >5 ticks (debugger, laptop sleep) -> skips ahead instead of fast-forwarding.

  - Every skill / product line / product / recipe / node has an `id` (unique within a world; equality is by id).

- Damage: base = tier + 1 for an item (tiers count from 0), times a colour multiplier `2^f`.
- Colours: a hue for every item (its making skill's colour: red 0, yellow 60, green 120, cyan 180, blue 240, magenta 300 -- `colorIndex * 60`, bright and dark count the same) and every monster type (any hue, any letter). Plus two colourless points: WHITE (shown white) and BLACK (shown BLACK_BRIGHT). Fists are BLACK.
- Hue vs hue: theta = (defender hue - attacker hue) / 180, wrapped into (-1, 1]. Piecewise ("option A"):
  - |theta| <= 2/3: f = sign(theta) * sin(|theta| * 3/4 * pi)
  - |theta| >= 2/3: f = sign(theta) * sin((1 - |theta|) * 3/2 * pi)
  - so +120 = x2 (red -> green -> blue -> red, cyan -> magenta -> yellow -> cyan), -120 = x1/2, 180 = x1, 0 = x1, +-60 = x1.63 / x0.61.
- Colourless: WHITE -> x2 vs every hue, x1/2 vs WHITE/BLACK. BLACK -> x1/2 vs every hue, x2 vs WHITE/BLACK. A hue against WHITE/BLACK: x1 (not specified; my pick).


## Next session: settings refactor (plan, not started -- yours to poke at)
Why: adding "Contrast tiers" touched ~10 places, all the same per setting: `Intent.SetX`, `Event.XChanged`, a `CharacterSnapshot` field, a `GameCharacter` field, a `GameServer` handler, a `WorldStore` migration + load SQL + save SQL, `Player` field + event branch + `welcome()` line + toggle method, a hand-built `SettingsMenu` row, `NetworkTest`'s hand-built snapshot. Goal: a new setting = one line defining it + the code that actually uses it.

Decided: settings the server needs are **per character** (stored in the world's db, next to `game_character`) and **stay on the server**. *(2026-10-24: display-only ones -- contrast tiers, time to goal, compact chat, light mode -- moved to the client's `settings.properties` instead, shared by all characters; this plan now covers color, running, auto-investigate.)*

- **Table (key/value, a.k.a. entity-attribute-value).** Good fit for preferences: few per player, read/written as a whole set, never searched by value, list keeps growing. The db can't type-check values (all text), so *all* reads/writes go through one typed definition in code. Not for real game state (position, xp, inventory, hp) -- those stay proper columns/tables.
  ```sql
  create table character_setting (
      character_id integer not null references game_character(id),
      key   text not null,
      value text not null,
      primary key (character_id, key)
  );
  ```
  Real foreign key (`foreign_keys` is already on in `SqliteStore`); `text` is SQLite's idiom for varchar; the primary key = one value per setting per character and easy upserts. Per-account settings would need an `account_setting` in `accounts.db` instead (SQLite can't do foreign keys across files) -- not needed now.
- **Typed keys in code** (an enum can't give each constant its own value type, a small generic class can):
  ```java
  // model/Setting.java -- the one place a setting is defined
  public final class Setting<T> {
      public static final Setting<Integer> COLOR = intRange("color.index", "Color", 0, 0, Intent.PLAYER_COLORS - 1).visibleToOthers();
      public static final Setting<Boolean> RUNNING = bool("running", "Running", false);
      public static final Setting<Boolean> AUTO_INVESTIGATE = bool("auto.investigate", "Auto-investigate", false);
      public static final List<Setting<?>> ALL = List.of(COLOR, RUNNING, AUTO_INVESTIGATE);

      final String key;        // in the db and on the wire: never rename once shipped
      final String label;      // settings menu
      final T defaultValue;
      final Codec<T> codec;    // text <-> value, allowed values, next/previous for Left/Right
  }

  // model/Settings.java -- one character's values
  public final class Settings {
      public <T> T get(Setting<T> setting);
      public <T> void set(Setting<T> setting, T value);
      public Map<String, String> asText();                       // save / send
      public static Settings fromText(Map<String, String> text); // unknown keys ignored, bad values -> default
  }
  ```
- **What each place becomes:**
  - 4x `Intent.SetX` -> one `Intent.SetSetting(String key, String value)`; the server checks it against the definition, refuses unknown keys / bad values.
  - 4x `Event.XChanged` -> one `Event.SettingChanged(String key, String value)`.
  - 4 snapshot fields -> `Map<String, String> settings` in `CharacterSnapshot`.
  - fields on `GameCharacter` / `Player` -> `Settings settings`; code reads `settings.get(Setting.RUNNING)`.
  - per-setting server handlers -> one handler; only `visibleToOthers()` settings (color) also set `infoChanged` so others see it.
  - columns + migration + SQL per setting -> `character_setting`, saved with the character like the other child tables (delete + reinsert in the same transaction).
  - hand-built `SettingsMenu` rows -> generated from `Setting.ALL` (label, current value, Left/Right = codec's next/previous).
- **Steps** (each keeps the build green):
  1. `Setting`, `Settings`, codecs (bool, int range) in `model`, with unit tests (parsing, defaults, rejected values, next/previous).
  2. World schema v10: create `character_setting`; copy the old columns over (`insert into character_setting select id, 'running', running from game_character`, same for `color_index` -> `color.index`, `auto_investigate` -> `auto.investigate`); then drop them (`alter table game_character drop column ...`, SQLite 3.35+; we're on 3.44). Load/save through `Settings`. Test: an old save with those columns upgrades with everyone's values intact.
  3. Protocol v5: `SetSetting` / `SettingChanged` replace the 4 intents + 4 events, the snapshot carries the map, one generic server handler. Color still reaches others via `EntityInfo`.
  4. Client: `Player.settings` -- change locally right away (like `setColor`/`toggleRunning` do now), send, server confirms. Readers use `player.settings.get(...)`; `SettingsMenu` rows come from `Setting.ALL`.
  5. Tests: one round trip over every setting for save/reload and for the wire, so new settings are covered for free. Update SCHEMA.md.
- Later, if wanted: an `account_setting` scope in `accounts.db` for settings that should follow you across worlds; enum-valued settings (a codec over an enum's values); per-setting "client only" flag if some ever shouldn't hit the server.

## Code structure
- Screen = a list of `Widget`s (`client.ui`): `CommandLine`, `MapView`, `ProgressBarView`, `TabBar` (headers, the inventory grid, the right box with the selected `Menu`), `MapDetailView`, `XpTrackerView`, `MessageLogView`, `KeyCommands`. Each one is given its `Rect` from `Layout` in `Main`. Each frame `Main` calls `draw` on each in order; each key goes to `onKey` in the same order until one returns true. So: earlier = gets keys first, later = drawn on top. A new screen element = subclass `Widget` and add it to the list in `Main.runClient`.
- New tab = subclass `Menu` (itself a `Widget`) and add it to the `TabBar`. Menus only get keys while focused; keys they return `IGNORED` for fall through to `KeyCommands` (wasd/q/g/...). `/` is caught by `CommandLine` first.
- Map drawing (+ home arrow, waypoints, popups) is `MapView`, skill colors/symbols `SkillStyle`, all screen positions and the map's view math `Layout`. The inventory is a `Menu` too (`InventoryPanel`) but `TabBar` takes it separately because its grid is always drawn.
- Packages (under `net.shchoo.scafe.scafe`), dependencies only point downwards in this list:
  - `model` -- shared game data: `Position`, `Skill`, `Product`, `ProductLine`, `Recipe`, `Node`, `Goal`, `Levels`, `ContentBatch`, `WorldContent`, `World`. Depends on nothing.
  - `generation` -- `WorldGenerator`, `SkillFactory`, `ProductLineFactory` (model only).
  - `protocol` -- the client/server contract: `Intent`, `Event`, `Wire`, `GameConnection`, `GameClock` (tick length), `Intent.MAX_QUEUED_STEPS`.
  - `server` -- `GameServer`, `GameCharacter`, `ActionProgress`, `NodeStates`, `Discovery`, `Walker`, `Pathfinding`, `LocalConnection`.
  - `persistence` -- SQLite stores. `net` -- `NetworkServer`, `SocketConnection`.
  - `client` -- `Player` (mirror + prediction), `Board`, `ConsoleAction`, `GameLog`/`MessageLog`, `Popup`, `XpTracker`, `SkillStyle`. Never imports `server`.
  - `client.ui` -- everything that draws. `Main` (root) wires it all together.
  - Tests live in the package of the thing they test.
- Rule of thumb: game rules go on the server and announce themselves with an `Event`; the client only reacts. Client-only messages (help, list, echo) use `GameLog.say` directly; server messages arrive as `Event.Message`.
